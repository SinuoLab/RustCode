> 生成日期：2026-10-18 · 面向对象：**需求 / 产品工程师（非 Rust 专家可读）**
> 当前 HEAD：见第 3.1 节 commit 索引（dev，已推送 origin 与 github 两个远端，两仓同 SHA；工作树仅有 1 个无关 WIP）
> 状态：**代码完成、CI 全绿、已在 dev**；文末列 4 项待产品侧研判的决策
> 复现与自查命令集中在同目录附属脚本 `docs/handoff/2026-10-18-release-pointers-verify.sh`（带联网参数可含 GitCode API 对账）

---

## 0. 一句话目标

让"下载安装"与"自我更新"永远指向**真实存在二进制**的版本；让本机推送 dev 不再被一个跑不动的自动发版卡死；并消除全量测试的内存峰值与两类假红。

---

## 1. 用户可感知的问题（为什么要做）

| # | 现象 | 谁受影响 | 严重度 |
|---|---|---|---|
| P1 | 不钉版本执行安装脚本，可能装到 **v6.2.1** 而不是最新的 **v6.2.3** | 所有新用户 | 高 |
| P2 | TUI 内 `/upgrade` 自我更新提示的版本，其在线 Release **一个二进制都没有**（只有源码包）→ 自我更新必然失败 | 已安装用户 | 高 |
| P3 | GitCode 在线服务抖动时，安装脚本回退到仓库内兜底源，而兜底源**没有最新版本** → 静默降级安装 | 所有用户 | 中 |
| P4 | 每次 `git push origin dev` 都被 pre-push 钩子里的自动发版拦截（本机构建跑不动）→ 推送被卡住，需手动加环境变量绕过 | 开发者 | 中 |
| P5 | 全量测试在小内存机器上可能 OOM；CI 里长期有偶发假红，导致该检查只能挂"不阻断" | 开发者 / CI | 中 |

P1–P3 是同一个根因的三个侧面：仓库里有三处各自独立的"当前版本"指针，互相之间没有一致性保证，也没有任何检查。

---

## 2. 根因（技术，可略读）

三处指针：

1. `Cargo.toml` 的 `[workspace.package].version` —— 真实版本（当时已是 `6.2.3`）
2. `release/index.json` —— 仓库内兜底源的版本清单（当时最高 `v6.2.1`）
3. 根目录的自更新清单 —— 客户端自我更新清单（当时同为旧版本 v6.2.1）

而 GitCode 在线 Release 上 **v6.2.3 的 8 个平台二进制是齐全的**。也就是"线上有、指针不知道"。

**结构性根因**：`latest.json` 历史上只有一个生产者——全矩阵发布脚本，而该脚本在 Linux 主机上跑不完（macOS 交叉步骤失败）。于是这个指针只能靠一台 macOS 主机刷新，长期冻结。这是机制缺陷，不是人为疏忽。

顺带查出的存量缺陷：`release/v5.1.0/` 目录**只有清单文件、一个二进制都没提交**，却被索引声明了 6 个平台——安装脚本会为它生成 6 条必然 404 的回退地址。

### 3.2 新增的防复发门禁（核心交付）

新增 `scripts/release-check-pointers.sh`（可离线运行）：

- 断言 Cargo 版本、兜底索引最高条目、自更新清单**三者版本一致**；
- 断言索引声明的每个平台与该版本清单的二进制键集**完全相同**（不许"声明了却没有"或"有却没声明"）；
- 断言清单点名的每个二进制**真的在版本库里**（未提交的产物 = 必然 404 的回退地址）；
- 断言自更新清单每条都是合法 sha256 + 非零 size；
- `--online` 额外对账 GitCode Release API 中"确实带二进制"的最高版本；
- `--sha` 判的是**将被推送的 commit**，不是工作树。

**接入位置**：`.githooks/pre-push`（推送前，可用环境变量 `RUSTCODE_PREPUSH_POINTERS=off` 关）与 CI job `release version pointers`。该 CI job **刻意不限制仓库**，因此在上游镜像仓库上也会真跑（既有的产物门禁因限定 canonical 仓库，在镜像上永远跳过）。

**发布流程改动**：发布脚本每次发布都刷新自更新清单；新增两个开关——一个用于补发或裁剪时防止指针回退，一个用于钉构建源 commit。

### 3.3 自动发版策略调整（对应 P4）

- 自动发版脚本：bump 版本前备份版本文件与锁文件，构建失败或产物缺失时**自动回滚**（否则工作树会停在一个没有产物的版本号上，被新门禁拒绝后续每一次推送）。
- pre-push 钩子：自动发版失败从"阻断推送"改为"**警告 + 继续推送**"，并打印重跑命令。设严格模式开关可恢复阻断（给真的会构建的发版机或 CI）。
- 理由：发布是推送的后续动作，不是前置条件；而本机 musl 交叉工具链未进 PATH、v6.2.3 起产物本就由 CI 构建，本机构建几乎不可能成功。

### 3.4 测试卫生（对应 P5）

- **OOM 防护**：峰值内存来自链接四个大二进制，不是编译小 crate。全量测试脚本与 CI 测试作业默认：并行度取 `min(nproc,2)`、对大二进制关调试符号、关增量编译。三项均可用 `RUSTCODE_TEST_JOBS` / `RUSTCODE_TEST_SYMBOLS=1` / `RUSTCODE_TEST_INCREMENTAL=1` 逐项放开。库 crate 仍带调试符号，backtrace 依旧可定位行号。
- **假红根因与修复**：两个测试模块各自维护一套串行化（一个用模块内锁、一个用测试框架的串行标记），**两把锁互不排斥**，两个测试照样并行改写进程级环境变量 `RUSTCODE_HOME`，导致读到彼此的主目录。修法是提取**一把进程级唯一锁**，两处都委托它。该反模式（"每个模块各上一把锁"）已写进 `AGENTS.md`。

| # | 决策点 | 选项 | 当前状态与建议 |
|---|---|---|---|
| D1 | 全量测试是否从"仅报告"转为"阻断" | (a) 维持 report-only；(b) 转 blocking | 两类假红的主要来源已消除（环境变量竞态已修）。剩余风险是 daemon 固定端口争用。**建议再观察 2-3 轮 CI 后转 blocking**，或先引入下一代测试运行器（每测试独立进程，能从根上消除端口/环境类假红）再转 |
| D2 | 是否引入下一代测试运行器（每测试独立进程） | (a) 引入；(b) 不引入 | 收益：根治端口/环境假红、测试更快；代价：新增 dev-dependency 与 CI 安装步。未实施，等意向 |
| D3 | 仓库兜底源的平台覆盖策略 | (a) 维持 3 平台（当前）；(b) 补齐 8 平台 | 当前兜底源只入库 linux-arm64 / linux-x64 / windows-x64（110 MB），macOS 与 FreeBSD 依赖在线 Release 加内置 GitHub 镜像。补齐会使仓库再增约 190 MB。**建议维持 (a)**，除非出现"在线源不可用且需要 macOS"的实际案例 |
| D4 | v6.2.4 的自动发版尚未跑通 | (a) 修本机构建后补发；(b) 只在 CI 发版 | dev 自 v6.2.3 tag 起已有多个源码提交，按策略应发 v6.2.4，但本机交叉构建不可用。已按"不阻断"放行推送。**建议 (b)**：发版统一走 GitHub runner，本机自动发版仅作兜底 |

## 6. 风险与回滚

| 风险 | 影响 | 回滚方式 |
|---|---|---|
| 指针门禁误报导致推送被拒 | 开发者推送受阻 | 一次性用环境变量关掉该门禁；门禁自身有 7 场景自测 |
| 自动发版改为不阻断后"忘了发版" | 版本落后 | 推送时有醒目警告；设严格模式开关可恢复阻断；发版机与 CI 建议设严格模式 |
| 关闭大二进制调试符号影响本地调试 | 大二进制无符号 | 用测试脚本的符号开关打开，或直接跑 cargo（不经脚本）；库 crate 符号不受影响 |
| v6.2.3 兜底产物入库使仓库 +110 MB | 克隆体积 | `git rm -r release/v6.2.3` 即可回退（在线 Release 仍是第一下载源） |
